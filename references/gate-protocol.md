# 门禁协议：退出码、报告、豁免、自愈

## 退出码（调用方必须区分，不许混读）
| 码 | 含义 | 调用方动作 |
|----|------|-----------|
| 0 | 通过（或全部为有效豁免） | 呈交用户放行 |
| 2 | 未通过（业务性） | 按归类处理：自愈类直接修；需决策类呈交用户 |
| 3 | 配置错（检查根本没跑） | **不许当成未通过去自愈，更不许当成通过**；修配置是门禁配置改动，属生成待批项，呈交用户 |
| 4 | 协议违例 | 停下，向用户说明被哪条不变量拦住 |

为什么：把 3 当成 2 处理，会去"修"一个根本没跑的检查；把 3 当成 0，
就是"门禁静默不跑而显示通过"——失效不可见，比失败危险得多。

## 报告结构（.pipeline/reports/）
- `gate-<关卡>-<时间戳>.json`：每次运行的归档
- `latest-<环境>.json`：放行校验读取的最新报告
- `evidence/<关卡>/<检查>.log`：原始输出。**原始日志不回传主会话**——
  主会话上下文是流水线里最稀缺的资源，门禁执行角色负责吃掉日志。

报告关键字段：`verdict`（pass/fail）、`counts`、每项 `status`
（pass/fail/exempted/degraded）、`classification`（self_heal/needs_decision/
out_of_bounds）、`degraded[]`、`config_drift`、`heal_exhausted`。

## 豁免协议（唯一合法例外通道，三要件缺一拒绝）
1. 人名（`--by`，脚本拒绝智能体署名）——责任落到人
2. 到期日（`--until`，未来的日期）——过期自动重新阻断，无需任何人记得
3. 理由（`--reason`，≥8 字）——到期审查者据此判断续不续

命令：`python .pipeline/scripts/gate.py exempt --check X --env dev --by 姓名 --until YYYY-MM-DD --reason ...`

例外中的例外：密钥扫描 `no_exempt`，豁免通道对其永久关闭。
理由：凭据一旦进版本库历史就等于已经公开，"这只是开发环境"在提交那一刻就失效了。

## 自愈协议（双上限，都是机制）
- 仅 `classification == self_heal` 的失败可自愈：修法确定、不改需求和架构。
- 上限一（记录式）：每修一轮先执行 `state.py heal-round --gate Gn`（轮次落盘，
  跨会话不重置）；第 2 轮记录后脚本即要求停止。
- 上限二（自动计数）：`gate.py run` 自动累计同一检查的连续失败次数，
  连败 3 次的自愈项自动升级为需决策——即使没人记录轮次也拦得住。
- **第 3 轮自愈不许发生**：两次针对性修复都没过，说明对失败原因的理解很可能
  是错的，第三次多半只是换个姿势撞同一堵墙，而用户看不到这个循环在烧钱。

## 让门禁变绿的手段一律禁止（违反即本次作废并上报）
降阈值、加 skip/xfail、注释断言、continue-on-error、`|| true`、--no-verify、
往忽略列表塞条目而不留理由和到期日、缩小扫描范围、把失败的测试改成断言
当前的错误行为。
它们的共同效果是门禁继续显示绿色但不再检查任何东西——而门禁是用户
唯一的质量控制点。觉得阈值不合理：作为需决策项呈交用户。
**用户改阈值是把关，智能体改阈值是绕开把关。**

## 外部工具的自评不能替代门禁
测试框架说"全过"、扫描器说"干净"，都只是检查项的输入；最终判定一律
以 `gate.py run` 的报告为准。外部工具不可用是常态：按适配器声明降级，
关卡上写明降级了什么；降级导致不达标 = 需用户决策，不许静默放行。
