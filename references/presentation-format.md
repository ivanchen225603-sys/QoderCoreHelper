# 关卡呈现格式（硬性，逐字照抄结构）

用户会重复看很多次，格式稳定才能快速扫读。每次呈现关卡，严格按此结构，
只替换内容，不改结构。

```
【关卡 Gn | <环节名>】判定：<放行待决 | 未通过 | 配置错>

产出（本次要你判断的东西）
- <产出 1>：<一句话摘要> — 路径
- <产出 2>：...

生成待批项（不混在产出里，单独列）
- <项>：<结论> — 理由与被否方案一句话

失败/需处理项（每项带归类与建议动作）
- [自愈] <项>：<原因> → 已自动修复并重跑 / 将自动修复（不问你）
- [需决策] <项>：<原因> → 选项：
    A. <修法 1>，代价约 <时间/范围影响>
    B. <修法 2>，代价约 ...
    C. 豁免（需你批准：记录你的姓名与到期日，状态显示"已豁免"而非"通过"）
- [越界] <项>：已做到最后一步可执行状态 — 要执行什么/影响什么/怎么撤回 — 由你执行

降级声明（没有就写"无"）
- <哪个检查> 降级为 <什么>，影响是什么

证据（给路径，不贴日志原文）
- 报告: .pipeline/reports/...
- 各检查证据: .pipeline/reports/evidence/...

下一步（可直接回答的选项）
- 回答"放行"并给出你的姓名 → 记录放行，进入 <下一环节>
- 回答"打回"+原因 → 返工 <本环节>
- 对需决策项回答选项编号（如"2A"表示第 2 项选 A）
```

## 规则与理由
1. **先给判定，再给细节**：用户的第一眼必须能判断"要不要现在花时间看"。
2. **归类由智能体做好**：用户不该自己去分"这算不算能自动修"——分错的代价是
   要么烧钱自愈死循环，要么把能自动修的事拿去烦用户。
3. **需决策项必须带代价**："覆盖率不够"不是可决策的信息；
   "补测约 40 分钟 vs 把退款移出本迭代 vs 走豁免"才是。
4. **豁免呈现为"已豁免"**：用户要一眼看出这次绿色里有多少水分。
5. **环境门禁与环节关卡分开呈现**：环境门禁呈现的是判定与证据；
   环节关卡（G1 需求+架构+原型合并、G4 评审、G6 发布准备）呈现的是产出全文判断。
   G1 一次呈现三份产出（需求、架构、原型）——分三次问，用户会在信息不全时逐个点头。
