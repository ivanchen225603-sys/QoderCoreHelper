# 平台能力适配表

先判断目标平台具备哪些能力，再决定做到哪一步。能力不足时降级，
但**必须显式声明降级了什么**——静默降级 = 用户以为机制还在，其实只剩约定。

| 平台能力 | 有 | 没有 |
|----------|----|------|
| 能派发子 Agent | 按角色派发，各自冷启动 | 单会话串行执行，工单账本照样要用——它同时是审计记录 |
| 能限定子 Agent 工具 | 白名单强制隔离 | 隔离退回成提示词约定，在派发包与关卡卡片上声明"隔离强度弱" |
| 能执行脚本 | 门禁、账本、探针都用脚本 | 门禁退化为逐条人工核对清单，明说这不等价 |
| 能开独立工作副本 | 并行 Agent 物理隔离 | 靠文件独占检查，控制并行度 |

能力探测结果由 `init` 写入 `.pipeline/config.json` 的 `capabilities`，
每次渲染派发包时据此打印隔离强度声明。

## 单会话降级的特殊规则：评审结论要保守
找不到问题时写：
> "本次评审在同一上下文中进行，隔离性弱于独立派发，未发现 ≠ 不存在。"

而不是"未发现问题"——后者会被当成质量证明。
同理：同一上下文写的测试，报告里注明"测试与实现同会话产生，
独立性弱于分别派发"。

## 当前平台（Qoder）的实测声明（2026-09 复验）
- 子 Agent 派发：可用（Agent 工具）。
- 子 Agent 工具限定：**可用**——自定义子代理（.qoder/agents/*.md）支持
  frontmatter 的 tools 字段，白名单由平台强制执行。首次交付时曾误判为
  做不到（当时只验证了通用 Agent 派发），复验 create-subagent 能力后确认；
  本次升级已把 7 个角色的原生定义（含白名单）纳入安装产物，隔离从纯约定
  升回机制。安装时仍校验白名单未被放宽，放宽即拒。
- 脚本执行：可用（python 在 PATH）。
- 独立工作副本：可用（git worktree），但默认串行认领，按需启用。
